# 选点与动作的双向推演、独立存储和按阶段交付（10.23）

**同一认知研究可以同时考虑点与动作，但一个阶段只能交付用户此时明确所求。**分开的不是思考，分开的是结果的身份、后台候选记录与对话交付时点。

- 先由两条独立路径分别寻找可改变位置。合并候选后，用相同的证据快照**并行**进行「独立组合/优先级竞争」与「后台动作可行性、效应与成本检验」。两者互不抄答案。二者完成后，成稿与审核共同使用完整成果，若动作检验发现原点不可达或只能产生转移而非净收益，应修正点的入选/排序而不是提前发动作。
- 在内部候选账本中，`point` 只表示被改变的现实状态、关系、条件或反馈；`action` 只表示如何实际使变化发生，明确 `depends_on` 指向 point；`plan` 只表示选择、顺序、资源、恢复与退出。新增独立 `action_preflight` 保留工作者回执和对应候选 action ID。预生成不是发布许可。
- `points` 答案应充分说明为什么值得、为何优先/靠后、证据边界、最强替代、组合价值，用**普通语言连贯展开**，不是后台表格或审核栏。具体动作、训练、日程、用户操作仍不公开。
- 用户接续 `actions` 且**未改变事实、目标和旧点**时，直接复用上轮已审计发布的 point 和已预研的 action 候选，不再次重跑独立选点、组合排名三项工作。此时独立挑战具体动作相对不作为的收益，并可针对实际新的可执行缺口定向补研；没有可用动作不假装完备。
- 用户接续 `plan` 同理引用先前已审核动作，不复述整份点/动作。**若新事实、目标或系统条件改变**，必须撤销旧的预演复用资格并重开受影响模型/点/动作。不能因为优化耗时绕过必要返工。
- 用户**明确要求完整方案**，可在同一回答中先点、再动作、最后计划，三个概念仍独立；如果仅说「下一步」，每次只推进一阶段。

效率来自**移除完全相同输入的重复搜索**和并行不同职责，而不是提前停止认知研究、限制干预点/动作数量、隐藏承重未知或依赖用户额度限制。


## 10.28 跨模型动作—干预点落地核验

行动必须先对应已审核的可改变位置，再解释该动作通过什么真实状态/关系改变产生结果、相对于不新增行动或最强备选增加什么收益、实施负担、失败及退出条件。成稿中自然讲出这条因果桥，不能仅写“对应点一”或换一个标签。独立审核者对**本轮实际交付的每一个动作**填写 `action_point_reviews`，核对已交付点与后台 `depends_on`、现实传导及用户可见的解释；若动作不能改变其声称的点、主要收益仅减少当前暴露而用户目标要求反应自身改变、或比零动作更差，则退回重做/明确有条件，不得在审核通过后添加一个未经核验的新动作。无动作阶段填写空列表，不为了字段存在编造动作。
