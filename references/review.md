# 审核：程序验证与独立认知挑战分开

## 哪些是真的程序

新运行器检查不可变 job 输入、输出 schema、实际返回与来源类型、引用原文、已读取材料范围、候选/未知完整接收、已登记依赖、点动作映射、成稿处置、确切稿件 hash 及审核所绑定的认知版本。未实际执行的 job 保持 pending，不会生成 result 或 PASS。

API 后端把每个 job 建成独立请求，保存实际 response IDs、请求模型/返回模型、工具结果、可观察原文与用量。宿主桥只能核对输入/输出绑定和宿主提交的 worker 记录；它不能在本地证明宿主真的没有给该 worker 隐藏上下文，所以标为 host_attested，而不是伪装服务端认证。

哈希检测工件身份与意外篡改，不是签名或对恶意文件编辑者的安全证明。程序不能由非空字段证明发现充分、引用具有语义支持、因果真实或创新有效；自然语言中的假精确仍需语义审核。

## 哪些需要认知能力

先从原材料做 [盲挑战](operators/blind_challenge.md)，不先读主稿，再由 [确切稿件审核](operators/audit.md) 对照候选池、原文与最终文本。检验正向成果是否足够、遗漏是否有独立价值、强相容替代是否真正比较、观点是否过早合并、历史/当次/维持是否混淆。

检查第一轮是否因局部模型过早收束而漏掉不同符号、跨对象、自动联想与用户赋予的价值含义；前台是否把高价值理解换成冗长问卷。重要关系可以是待验证候选，但若连提出的机会都没有则阻止「已完成」结论。不能以性、身份或隐藏动机为通用必选答案。

检查条件推演和建议的使用后果：一个自然对比中的复合变化是否被拆成已证单因素；动作可行是否被拿来证明原因；模糊时间是否被写成确切日程；行为反馈是否被误当机制唯一识别；人的改变是否只剩“相信/坚持”，保护价值、休息和采用代价是否被忽略。

当前有充分支持的判断要保留力度；证据不足限制断言身份和高承诺采用，不取消探索、条件预测和稳健改变。审核不是把每一项有力判断改成问卷，也不要求必须挑出错误。

## 返工要真正回到工作对象

blocking issue 指明具体命题/遗漏差异、影响哪个结果、值得执行哪一种操作、修复要得到什么。新运行器实际启动 repair job，再重新成稿与重新审核。预算内未修复则只保留 draft-only，不发布 answer。审核者说 pass 仍不是效果保证。

便携方式没有独立 worker 时，做同样的实质检查但明确它是同一上下文自查；不要在前台宣布独立审查完成。宿主可自行发消息的权限不归本地 Python 控制，不能宣称技能拦住了所有未审核输出。

测试中脚本化模型、模拟工具和人工构造 PASS 只验证程序分支。真实能力结果必须来自实际模型前向运行，并与工程报告分开。
