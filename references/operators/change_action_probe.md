# 独立后台动作可行性检验：在选点时反向校正点的价值

你收到的是已独立顺向/逆向生成、但尚未确定最终优先级的 `point` 候选池。你的任务是**后台验证这些位置是否真的可改变**，不向用户提前交付任何动作，也不因为方便执行就自动提高某点排名。

1. 对各项有独立价值的点，考虑能使该位置发生变化的不同具体动作或环境条件；核对入口、可达性、权限、资源、代价、负面效应、保护价值、失败退出条件和与“不新增操作”相比的增量。没有证据时提供有边界的动作构造，不冒充效果已证明。
2. 动作可改变的究竟是起因、维持过程、使用者接受程度还是观测数据？如果原点只有抽象目标没有现实可达位置，生成竞争未知或修正机制，而不是凑一项口号式动作。
3. 同时考虑点与点联合才能有效的动作、互相冲突的动作、直接改变环境的替代，以及更少负担的正常继续。除时间先后，还考虑能力变化、信任、接受、反馈如何形成下一次可继续的条件；不将小步渐进设为唯一模式。
4. 保留分别代表候选位置的 `kind=point` 和具体行为/规则/环境安排的 `kind=action`；**返回的新行动必须标记为 `kind=action`，通过 `depends_on` 指向现存真实 point ID**。若必须先发现一个新点，可在同份 work 中新建 point local_id 并由动作引用，但不要复制同义点。
5. 检查可能的实际效果，再把动作的可达性、反例和下游反馈用于**重新评价点的优先次序**。报告 `summary` 中指出哪些点可达、哪些只在条件成立时可达、哪些组合需要后续补充。若没有可靠的新增动作，填具体 `no_increment_reason`，不为了测试配额制造动作。

本工作只为**内部选点审查和后续动作阶段**提供候选。当前若是 `points` 阶段，绝不把行动、日程、口令、训练或计划以正文交给用户；行动可以先存在候选存储中，用户明确推进到 `actions` 阶段后才选择、审查、发布。发现新事实或被挑战的点时应重新评估受影响候选，不因为已预生成就自动采用。

返回 `work`；所有主张仍受事实与推断边界约束。不可在用户未要求时执行实际外部操作。
